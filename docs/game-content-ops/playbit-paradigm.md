# Playbit 游戏内容范式

这份文档是游戏内容、用户端、管理端和后端实现的共同约束。它把 Playbit 已经形成的产品判断固化下来，避免后续为了扩展多人、推荐或权益而把用户体验变重。

## 1. 一句话定位

Playbit 给用户一张抽到就能玩的社交游戏卡；后台负责把玩法骨架、内容版本、工具、审核、分发和复盘组织成可持续运营的系统。

用户侧轻，后台侧重。用户不需要理解 L0、L1、L2、推荐分数、冻结次数或内容版本。

## 2. 用户体验范式

- 进入「开一局」后，抽到卡即进入进行中，不增加「开玩这张」的确认层。
- 游戏卡必须先完整可读，再提供工具和结果操作；卡片是主角，工具不应抢占规则正文。
- 主持人在现场带玩，其他人不需要登录、加入房间、同步状态或安装 Playbit。
- 游戏结果由主持人登记。Playbit 记录主持人的声明，不判断线下事实。
- 结果登记、证书分享、权益结算彼此可独立触发；游戏不自动创建合约，不自动下注，不自动发行共享权益。
- 刷新或离开未完成的轻游戏默认丢弃，不伪装成可恢复房间。
- 「换一张」是主要的放弃动作，必须记录为 rerolled，但不能把跳过误算为开始或完成。

## 3. L0 / L1 / L2 的职责

这三层是研发和运营语言，不是用户界面信息架构。

### L0：核心互动循环

说明为什么这个机制会让人想继续玩，例如约束冲突、检索枯竭、累积负荷、信息缺口、心智博弈、自我揭示、联想重构、共创接力、感知动作博弈。

L0 用于去重、研究和推荐解释，不直接承载用户内容，也不直接决定一张卡的文案。

### L1：可重复使用的玩法骨架

定义参与人数、轮次、主持人行为、胜负或完成条件、时长和工具声明。例如「三句话一句假」「共同点」「海龟汤」属于玩法骨架。

L1 是收藏、偏好、冷却和推荐的主要归属。用户收藏的是喜欢的玩法类型，而不是某一条具体题目。

### L2：一次可消费的内容实例

定义某一局的题面、答案、关键词、情境或限制条件。L2 隶属于具体 L1 版本，可以永久不再展示，也可以按策略冷却后再展示。

L2 发布后不可原地修改。编辑必须生成新版本；已经开始的游戏永远读取开始时的快照。

## 4. Tool 范式

Tool 是共享的现场辅助能力，不是每张卡独立开发的功能。

- 初期工具：计时器、计数器、记分牌。
- 卡片版本声明 `required` 或 `optional` 工具；必需工具不可用时不能进入候选，非必需工具不可用时退回口头玩法。
- 工具在卡内面板或底部抽屉打开，不跳出游戏流程。
- 工具状态只属于当前本地游戏，不形成资产、积分、推荐事件或合约状态。
- 记分牌保留参与者快照和排名扩展位，但暂不实现实时多人房间。

## 5. 内容研发与发布范式

Agent 负责检索、候选改写、结构化和相似内容提示；人工负责玩法可玩性、表达风险、文化适配、重复度、工具声明和发布决策。

内容状态是：`draft`、`pending_review`、`changes_requested`、`approved`、`published`、`paused`、`retired`。审核对象必须是具体的版本，不是会被后续编辑覆盖的抽象记录。

发布生成不可变的发布快照。分发、事件、结果和推荐都引用快照或版本 ID；淘汰保留历史，不删除用户行为证据。

管理端首版是 `/studio` 的 PC 工作区，不做 SaaS 卡片堆叠，而围绕内容库、版本、试玩、审核、发布和复盘组织工作。

## 6. 推荐与复盘范式

- `exposed`、`started`、`rerolled`、`tool_opened`、`completed`、`abandoned` 必须分开记录。
- 事件使用服务端签发的 `actor_key` 和客户端 `client_event_id` 幂等，不使用 IP/UA 作为用户身份。
- 事件上报失败不阻塞抽卡和开始；客户端短队列可重试。
- L1 冷却和收藏偏好分开：收藏表达喜好，不解除 L2 永久消费或冷却规则。
- 推荐先做透明的规则候选过滤，再接模型或学习排序；超时返回最近审核通过的基础候选，候选为空返回明确空状态。
- 推荐读取聚合表，不在每次抽卡时扫描事件明细。

## 7. 游戏、证书与权益边界

游戏是轻量内容体验；合约是签字和承诺的仪式；证书是结果传播内容；权益是独立资产。

- 游戏结果可以不关联合约。
- 独立结算可以填写备注，权益关联可为空，也可以关联游戏结果、证书或合约。
- 不创建共享券。输方给赢方发独立权益券，发行和领取是明确的资产动作。
- 未来多人模式只预留参与者快照、排名和结果结构；不提前实现房间、邀请码和实时同步。

## 8. 视觉范式

用户端延续首页的专业白底、克制蓝、珊瑚和浅金层次。游戏卡承担内容主视觉，工具和状态反馈使用清楚的局部反馈，不使用厚重后台蓝卡或手游式复杂装饰。

管理端可以更密集，但仍使用同一套色彩、圆角、阴影、排版和状态语义。页面应优先展示当前工作和下一步动作，不用装饰性指标占满首屏。

## 9. 不可提前实现的能力

除非产品边界重新确认，否则不要因为数据库预留就实现：游戏房间、参与者入场、游戏卡分享、平台裁判、游戏内下注、真实货币、全局排名、自动合约、自动权益和把 L0/L1/L2 展示给用户。
