# Phase 1：数据与状态基础

## 1. 目标

建立内容系统最小可靠内核，使开发 Agent 可以创建、审核、发布和运行一张游戏卡，并正确记录用户对 L1/L2 的暴露和消耗状态。

本阶段不做复杂推荐模型，不做管理端完整视觉，不做 Agent 自动运行。先让数据边界和状态变化稳定。

## 2. 数据对象

### 2.1 内容对象

```text
content_source
  └─ raw_game_sample
       └─ raw_l1_rel
            └─ l1_game
                 ├─ l1_game_version
                 ├─ l1_l0_rel
                 ├─ l1_scene_rel
                 ├─ l1_tool_rel
                 └─ l2_content
                      └─ l2_content_version
```

`raw_l1_rel` 必须是多对多关系。不能在原始样本上只放一个 `normalized_l1_id`，因为多个原始玩法可能归并为一个 L1，一个样本也可能启发多个 L1。

### 2.2 L1 最小字段

- `id`、`code`、`name`。
- `lifecycle`。
- `min_players`、`max_players`。
- `duration_min`、`duration_max`。
- `props_requirement`、`movement_level`、`outcome_model`、`host_required`、`certificate_eligible`。
- 主 L0 和次 L0 关系。
- 场景适配关系。
- 编辑备注。

### 2.3 L1 版本字段

规则文本不能直接覆盖。每个版本至少保存：

- `short_rule`：卡面主规则。
- `rule_detail`：详细执行规则。
- `completion_condition`：完成或胜负条件。
- `failure_condition`：失败、超时和放弃处理。
- `display_hook`：卡面 Hook。
- `information_structure`：隐藏、公开、逐步揭示等结构化信息。
- `control_structure`：轮流、同时、主持、随机等控制结构。
- `participant_model`：参与者角色和视角。
- `version_no`、`change_note`、`published_at`。

`participant_model` 需要能表达主持人、参与者、轮流/同时行动、可选人数和是否存在自然胜负。它是玩法协议的一部分；未来增加多人参与时，优先扩展这个结构和现有对局领域，不新增 L3。

`outcome_model` 只决定结果记录方式，不承担下注或权益资格。SELF_REPORTED_WINNER 用于双人胜负登记，RANKED_RESULT 用于多人计分和排名，二者都可以生成证书；NO_WINNER 和 SHARED_COMPLETION 仍然可以正常抽卡和完成。游戏卡不做参与者扫码、加入或双方确认；双方确认只属于正式 Agreement 流程。所有游戏卡都不自动进入 Agreement、Coupon 或 Flip。

### 2.4 L2 内容包

L2 使用 `payload jsonb` 保存玩法专属结构，但必须由 `content_type` 约束其形状。例如：

```json
{
  "contentType": "STORY",
  "prompt": "一个人走进酒吧……",
  "answer": "真实原因……",
  "hints": ["提示一", "提示二"],
  "hostResponsePolicy": ["是", "不是", "无关"]
}
```

L2 必须能单独审核、发布、冻结、消耗、暂停和退役。内容版本发布后不可原地修改。

## 3. Game Card Instance

用户点击抽卡时，服务端或受控的内容服务先生成短期 Card Delivery：

1. 根据人数、场景和已发布状态生成候选。
2. 过滤用户当前不可用的 L1/L2。
3. 选择一个 L1 版本和一个 L2 版本。
4. 固化 Tool 配置、卡面文案和推荐原因。
5. 返回可验证的卡片快照和短期交付标识。

普通匿名轻玩不创建 game_card_instances 数据库记录。主持人保存结果/证书、登录后保留历史或进行服务端可恢复操作时，才创建持久化 Game Card Instance；它必须保存 l1_version_id 和 l2_version_id，不能只保存当前 L1/L2 ID。用户开始游戏后，后台编辑不得改变本局内容。

匿名用户可以生成短期 Card Delivery，但不创建用户账号、Agreement 或持久化游戏局。需要持久化的收藏、历史、结果证书和发券动作再关联登录用户。

game_card_instances 是内容快照和服务端恢复边界，不是房间或完整游戏局。结果记录、参与者显示信息、分数、排名和证书快照属于轻量 Game Result 领域；正式彩头、权益、邀请和翻盘只属于现有合约产品，游戏卡不自动创建它们。

## 4. 游玩归因状态

```text
CREATED → STARTED → COMPLETED
                    └→ ABANDONED
CREATED ────────────→ CANCELLED
```

- `CREATED`：卡片已经生成，但用户还没有开始。
- `STARTED`：用户点击开始并进入游戏。
- `COMPLETED`：游戏按照规则结束。
- `ABANDONED`：用户开始后主动离开或超时未完成。
- `CANCELLED`：系统或用户在开始前取消。

普通匿名游玩不建立持久化游戏局。客户端或短期服务状态可以记录这些事件阶段，事件使用临时 Play Session ID 归因。它不能替代内容审核状态、用户曝光状态或 Agreement 状态。

## 5. 用户曝光和复用状态

`user_l2_exposures` 是线上抽卡的聚合状态，不从事件明细实时计算。

需要维护：

- 展示、开始、完成、跳过次数。
- 最近展示、开始、完成时间。
- `next_available_at`。
- `exhausted` 是否永久消耗。

展示和游玩必须分开处理：

```text
展示但未开始 → 短冷却
开始后退出   → 中冷却
完成         → 按内容复用策略决定冷却或永久消耗
主动跳过     → 弱负反馈和短冷却
```

收藏写入 `user_l1_preferences`，代表用户喜欢某种玩法类型。收藏不能绕过 L2 的永久消耗和冷却规则。

### 5.1 L1 冷却与 L2 消耗必须分开

`user_l1_exposures` 控制玩法骨架的重复展示，`user_l2_exposures` 控制具体内容的展示、冷却和永久消耗。

- L1 冷却解决“连续抽到同一种玩法”的疲劳问题。
- L2 规则解决“这条海龟汤已经玩过”的内容重复问题。
- 用户玩过某个 L2 后，可以在冷却结束或永久消耗规则允许时继续玩同一 L1 的其他 L2。
- 匿名用户也必须写入这两张聚合表，主键使用稳定的 `actor_key`；登录后再补写 `user_id`，不能只给登录用户做去重。
- 收藏只影响 L1 偏好排序，不绕过任何 L1/L2 的可用性判断。

## 6. 幂等和并发

- 创建游戏局使用请求 ID 或客户端事件 ID 幂等。
- 更新用户曝光状态时使用事务或原子 upsert。
- 并发抽卡不能让同一用户同时拿到同一条不可重复 L2。
- 完成事件重复提交不能重复增加完成次数。
- 发布操作必须检查版本状态并写入发布时间。
- 管理员修改复用策略必须写审计记录。

## 6.1 匿名身份、请求幂等与登录续接

`actor_key` 是服务端认可的匿名设备/会话身份，不能直接使用 IP、UA 或前端展示昵称。登录后以用户身份为主，但保留原 `actor_key` 作为同一段体验的关联键。

抽卡接口必须接收调用方生成的 request_id。匿名短期交付使用短期缓存或签名响应保证同一请求重放得到同一张卡；需要持久化时，服务端用 (actor_key, request_id) 唯一约束保证只生成一个 Game Card Instance。事件上报另用 (actor_key, client_event_id) 幂等，不能拿事件去重表替代抽卡请求幂等。

登录续接按事务完成：

1. 将当前匿名 Card Delivery 或已创建实例的 `user_id` 补齐；若已经进入共享/可恢复对局，再保留原 `actor_key`、卡片实例 ID 和版本快照。
2. 将匿名 L1/L2 聚合状态合并到用户状态；计数采用明确的合并规则，不能简单覆盖较新的用户记录。
3. 收藏、历史和推荐偏好只在登录成功后持久化，匿名期间只用于当前设备/会话的短期推荐。
4. 登录失败或续接过期时，当前卡片仍可按匿名实例继续完成，不能把用户带回首页重新抽卡。

## 6.2 内容版本和审核边界

发布对象必须是具体的 L1/L2 版本。审核记录需要同时保存父实体、`target_version_id`、提案 ID、审核人、决定和理由；只审核父实体而不锁定版本的记录无效。

已创建的卡片实例和已开始的游戏局永远读取自己的版本快照。后台发布新版本只影响新实例；暂停或隔离内容阻止新抽卡，但不篡改已经开始的游戏局。

## 6.3 抽卡 API 的失败和降级

抽卡服务返回 Card Delivery 或持久化卡片实例状态和 `request_id`，前端只依赖用户可玩的卡片字段，不暴露 L0/L1/L2 的研发术语。

- 推荐计算超时：读取最近一次经过审核的基础分发结果，仍按当前内容状态和冷却再次校验。
- 候选为空：先提示“暂时没有合适的新玩法”，允许稍后再抽；只有明确标记为保底且没有违反永久消耗规则的内容才可作为保底。
- 所有候选被冻结、隔离或离线：展示可重试状态，不伪造成功抽卡，也不把用户送回首页。
- 网络中断：已生成的实例可以通过 ID 重取；未确认的抽卡请求用同一个 `request_id` 重试。
- 普通匿名轻玩不要求通过数据库 ID 恢复；客户端可用签名快照继续当前卡，只有分享或升级后的持久化对局才要求服务端恢复。
- 事件上报失败：先在客户端有限队列重试，不能阻塞用户开始游戏；服务端最终聚合允许短暂延迟。

## 7. Phase 1 验收

- 可以创建一个 L1 和多个 L1 版本。
- 可以为一个 L1 创建结构化 L2。
- 可以发布一个 L1 版本和一个 L2 版本。
- 可以生成包含版本快照的游戏卡实例。
- 可以开始、完成、放弃一局游戏。
- 可以记录用户 L1 收藏和 L2 暴露状态。
- 重复请求不会重复创建局或重复累计行为。
- 后台修改内容后，已创建的游戏局仍能还原原内容。
- 抽卡路径不扫描 `game_events`。
- 匿名用户连续重试同一个 `request_id` 只得到一个卡片实例。
- 同一匿名 `actor_key` 也会受到 L1 和 L2 冷却约束。
- 登录后能续接当前卡片；已经进入共享或可恢复对局的记录不会丢失版本快照。
- 审核记录能区分原始样本审核和具体 L1/L2 版本审核。
- 推荐超时、候选为空和离线时都有可恢复的用户状态。

## 6.4 多人预留，但不实现房间

首期不实现房间、在线同步或多人状态机。主持人自己查看 Card Delivery 并负责口头推进；现场其他人不需要查看卡片、不需要扫码、不需要登录，也不需要创建游戏局。只玩游戏时，卡片只承担主持人的现场提示。

游戏结束后，主持人可以选择“记录结果”：双人登记胜负或平局，多人记录分数和排名，再生成结果/比赛证书。证书是对主持人提交结果的展示和传播，不是平台裁判，也不自动产生权益。

证书和结算权益是两条独立链路。主持人可以分享证书；履约方可以从独立入口发起结算，不要求胜方进入原游戏卡页面。二维码/链接只用于证书或结算领取，不用于分享游戏卡。每张券都单独保存 issuer/provider、holder、权益条款和可选的来源结果/证书；胜方扫码领取并同意后绑定账号并生效。多人时也按每个发券人与收券人生成独立券，不生成共享券。

如果参与者需要完整的签署、履约或翻盘，应主动进入现有合约产品。游戏卡结果可以作为上下文，但不自动创建 Agreement。

内容系统只预留：

1. L1 participant_model 能表达主持人、参与者、人数和行动方式。
2. Card Delivery 只负责主持人本地取得可复现的卡片快照，不生成游戏邀请或参与者入口。
3. 持久化 Game Card Instance 可以关联 Game Result Record 或 Certificate；普通多人计分只保留临时 Play Session ID，只有主持人主动保存结果或证书时才持久化。

不要在内容系统新增房间、stake、claim、coupon 或 settlement 实体。独立权益券由现有合约/权益域负责；结果服务只保存游戏结果和证书所需的快照。未来多人同步另立游戏运行域，不改变内容分层。
