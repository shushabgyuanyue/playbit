# 游戏卡内容系统设计审查

审查对象：`game-content-ops-design.md`、Phase 1-4 文档和 `game-content-ops-schema.sql`
审查视角：内容运营、用户体验、数据推荐、数据库性能、开发落地
审查状态：第一轮结论已落地；以下内容保留为实现约束与生产上线门槛

## 1. 高优先级问题

### 1.1 L1 级曝光状态缺失

当前有 `user_l1_preferences` 和 `user_l2_exposures`，但没有 L1 级的最近展示、短期冷却和连续重复控制。只记录 L2 无法保证“上一张是海龟汤，下一张不要仍然是海龟汤”，也无法准确执行“最近展示过相似 L1”的规则。

处理：增加 `user_l1_exposures`。收藏和曝光继续分表，避免把用户喜欢某个玩法与系统暂时不应展示它混在一起。

### 1.2 匿名抽卡缺少幂等身份

设计允许匿名用户抽卡，但 `game_card_instances` 只有可空的 `user_id`。匿名刷新、网络重试或同一入口重复请求无法稳定识别为同一个请求，可能产生重复卡片和重复展示。

处理：卡片实例使用 `actor_key + request_id` 做幂等键。`actor_key` 可以是登录用户 ID，也可以是匿名会话生成的短期随机值，不创建 guest user。

### 1.3 审核没有绑定具体版本

文档要求已发布内容不可原地修改，但 `editorial_reviews` 当前只指向实体 ID，L1/L2 版本只有 `published_at`，没有明确的版本审核状态和审核人。

处理：为版本增加 `DRAFT / REVIEW / APPROVED / PUBLISHED / REJECTED` 状态；审核记录必须保存目标版本 ID、审核人和决定时间。实体生命周期只表达整体状态，版本状态表达具体可发布版本。

### 1.4 分析维度与日报表不一致

分析页面承诺按场景、人数、用户 cohort、版本、推荐策略和实验分组下钻，但当前 `l1_daily_metrics` 和 `l2_daily_metrics` 只有日期和内容 ID。继续按现在的表开发，后面一定会返工统计层。

处理：线上主库保留 L1/L2 全量核心汇总；带多个维度的分析进入分析副本或专用 rollup，第一版用 `recommendation_daily_slices` 保存场景、人数、cohort、版本、策略版本和实验分组。不要把所有高基数维度塞进抽卡事务。

### 1.5 复用策略允许重叠

`content_reuse_policies` 和 `distribution_policies` 可以存在多条同时生效的记录，文档没有定义冲突解决顺序。管理员调整后，系统可能无法判断应该使用哪条冻结时间或权重。

处理：规定精确优先级：L2 + 场景 > L2 > L1 + 场景 > L1 > 全局；同一作用域只允许一条未结束策略。修改使用新记录和 `effective_to`，不能覆盖历史。

### 1.6 分层方向结论

L0/L1/L2/Tool 的主分层方向是正确的，不建议增加 L3：

- L0 只回答“为什么这类互动可能成立”，属于研究、聚类和分析语言。
- L1 是可重复运行的玩法协议，必须包含参与者角色、人数、行动、信息和结束条件。
- L2 是一次具体游玩的内容数据，不能偷偷承担规则变化。
- Tool 是计时、揭晓、私密查看等运行能力，不能承担参与者身份、权益所有权或结算。
- Card Delivery/Game Card Instance 是已发布内容的运行投影，不是新的内容层，也不是 Agreement。

真正需要修正的是边界：匿名轻玩不应因为抽到一张卡就创建持久化游戏局；只有主持人记录结果/证书、登录历史或服务端恢复等边界才固化卡片快照。对外分享的是证书或结算链接，不是游戏卡。

### 1.7 未来多人模式不应复制一套业务域

当前产品已经有 Agreement(source=card)、Coupon、Flip、邀请和结果登记。游戏卡的目标形态应是“一个主持人本地带玩 + 可选结果/比赛证书”，不需要房间、大厅、座位、准备阶段、卡片二维码传播或平台裁判。证书和结算权益可以通过各自链接传播，但不传播游戏卡。

游戏卡不承载下注或共享权益。双人和多人都可以只在线下约定权益，Playbit 只提供可选的结果记录、计分榜、排名和证书。结果确认后，输方可以主动给指定胜方发一张独立权益券，每张券有唯一 issuer/provider 和 holder；需要正式签署、履约或翻盘时，再进入现有合约产品。内容运营系统不应新增 stake、claim、coupon、settlement 或 room 表。

开发预留只需要三件事：L1 版本保存主持人/参与者模型，Card Delivery 能在主持人本地生成可复现卡片快照，主持人结果记录能保存卡片版本、参与者、分数和证书快照。独立结算券和领取记录属于现有权益域，不进入内容卡分层。

## 2. 中优先级问题

### 2.1 用户侧缺少无候选和失败体验

设计写了候选过滤和永久消耗，但没有规定候选为空、推荐服务超时、离线或所有候选被冻结时用户看到什么。

处理：必须有本地可用的已审核保底卡、静默重试和明确的“换一张”反馈。保底卡也要遵守安全、人数和永久消耗约束，不能用已永久消耗内容硬顶。

### 2.2 登录续接没有写入游戏卡设计

匿名用户收藏、分享、保存主持人结果或发起独立结算时需要登录。当前文档只写“再要求登录”，没有定义登录后如何把匿名会话、卡片实例和当前游戏状态接回去。

处理：登录续接只迁移当前匿名会话的可迁移状态，不能把匿名行为伪造成历史用户行为。登录后保留当前卡片和表单，事件仍使用原始 Card Delivery 或持久化 instance ID。

### 2.3 事件定义还缺少统计口径

`IMPRESSION`、`REVEAL`、`START`、`COMPLETE` 的触发时机需要固定，否则不同前端实现会产生不可比较的数据。

处理：在事件字典中写明每个事件的触发动作、幂等键、分母和归因窗口。尤其要区分“卡片进入视口”“卡片真正被看见”“点击开始”和“规则完成”。

### 2.4 Agent 提案的当前状态不够明确

Agent 任务有运行状态，但提案本身没有独立状态。一个任务可以生成多个提案，审核后也需要知道哪个提案已接受、哪个被拒绝。

处理：给 `agent_proposals` 增加 `OPEN / IN_REVIEW / ACCEPTED / REJECTED / SUPERSEDED` 状态，以及解决人和解决时间。

### 2.5 管理端角色只有产品描述，没有权限模型

文档区分内容编辑、审核、数据和分发管理员，但数据库没有角色和授权关系。

处理：增加最小的 `admin_roles` 和 `admin_user_roles`。发布、策略调整、实验结束和内容退役必须由服务端按角色校验，不能只靠页面隐藏按钮。

## 3. 内容运营视角的缺漏

- 需要看到 L1 的 L2 供应量、可用量、已消耗量和预计耗尽时间。
- 需要看到一个玩法是否因为“缺内容”而无法继续分发。
- 需要有内容隔离或 quarantine 状态，处理用户举报、版权疑问和安全风险。
- 需要支持“同一 L1 的内容质量不均”诊断，不能把 L1 平均分掩盖 L2 问题。
- 需要记录运营手动降权的原因，否则推荐表现无法解释。
- 需要有小流量发布、暂停、恢复和回滚的完整时间线。
- Agent 采矿结果必须保留来源、证据和版权判断，不能只保存改写后的玩法。

## 4. 用户视角的缺漏

- 首次抽卡不能要求用户先理解收藏、冷却和推荐机制。
- “收藏玩法”是用户语言，不能在前台使用“收藏 L1”。
- “再来一局”要明确是同一种玩法换一个内容；“换一张”才是换玩法。
- 跳过不能让用户产生“我在训练一个不可逆的标签”的感觉。
- 卡片被永久消耗后，用户仍可以继续玩同一 L1 的其他内容。
- 推荐失败时不能把后台错误、候选不足和内容耗尽直接暴露给用户。
- 游戏卡不对外分享；对外分享的只能是冻结的证书或独立结算链接。证书/结算内容必须引用明确的结果、权益和版本快照，不能让收件人拿到另一条结果或另一张券。

## 5. 设计取舍确认

- 保留 L0/L1/L2，不增加 L3。
- 增加 L1 曝光聚合和 Game Card Instance 幂等字段，避免重复和冷却失效。
- 内容版本、审核状态、运行状态、曝光状态继续分开。
- 推荐先规则化，模型只改变排序，不突破审核、复用、安全和用户权限边界。
- 线上主库服务抽卡和状态，分析副本服务高维度报表。
- 管理端优先做 L1 工作台、游戏卡实验室、审核队列和分发策略，不先做大而全的 BI。
- 移除内容系统的持久化 game_sessions；普通多人计分只使用临时 Play Session ID，只有用户主动保存结果时才创建轻量结果记录。
- 增加 L1 结果模型和 certificate_eligible，明确双人结果确认和多人排名默认产出证书，不自动发行权益卡。

## 6. 修正后的进入开发条件

只有满足以下条件，Phase 1 才算完成：

1. 同一匿名或登录 actor 的重试不会重复创建卡片实例。
2. L1 和 L2 都能独立执行冷却、永久消耗和恢复。
3. 审核记录明确指向具体内容版本。
4. 管理员角色能在服务端生效。
5. 抽卡失败、候选为空和登录续接都有明确行为。
6. 核心事件的触发和统计口径固定。
7. 分发策略冲突有确定的优先级和唯一生效规则。
8. 多人排名、双人结果登记和普通轻玩都不会自动进入 Agreement/Coupon 资产流程；独立权益券必须由输方主动发给明确的胜方。

## 7. 本轮最终收敛

### 7.1 保留的最小产品闭环

```text
抽卡 → 立即游玩 → 主持人可选登记结果
                    ├─ 生成并分享结果/比赛证书
                    └─ 履约方可从独立入口发起一对一结算
```

正式签约仍然是另一条完整链路：创建 Agreement → 双方签字 → 进行中 → 结果 → 履约/翻盘。不能为了复用卡片而把游戏卡变成轻量合约，也不能为了复用证书而把两条链路强行合并。

### 7.2 应删除的游戏侧能力

- 游戏开始前的下注、加注、权益选择和双方确认。
- 房间、大厅、座位、加入、准备和在线同步。
- 游戏卡内的 Coupon、Flip、共享券和自动结算。
- 强制另一位参与者登录或回到原卡确认结果。
- 全局排行榜、赛季、积分成长和游戏资产进度。

### 7.3 必须保留的后台能力

- L0/L1/L2/Tool 作为研发和推荐语言，但不暴露给用户。
- Card Delivery、版本冻结、L1/L2 曝光聚合和追加事件。
- 主持人结果快照、证书快照和可选独立结算的引用关系。
- Agent 提案、人工审核、真人试玩、分发冷却和可解释推荐。
- 正式 Agreement/Coupon/Flip 的独立资产边界。

### 7.4 当前仍需防止的技术债

`GameResultRecord` 是结果快照，不是房间；`Certificate` 是结果的传播视图，不应再建一套独立比赛资产；`SettlementRequest` 属于权益域，不应进入内容运营库。三者只通过可选 ID 引用，不要互相嵌套状态机。

管理端先做总览、内容库、游戏卡实验室、审核与试玩、分发与分析五个工作区。Agent 任务、标签和状态应作为工作视图或系统设置，避免后台页面数量反过来塑造产品复杂度。

### 7.5 本次业务澄清

- 主持人是唯一需要打开游戏卡的人。参与者在线下同步，不通过二维码查看卡片，不进入游戏卡页面，也不需要加入、登录或确认。
- 游戏结果从游戏流程产生时，来源就是 `GameResultRecord`；它不应偷偷创建 `Agreement`。独立结算也可以脱离游戏结果，权益转让备注可填可不填。
- 对外传播的对象只有结果/比赛证书和独立结算领取链接。证书分享与权益发放互不阻塞。
- 券可以没有关联合约。游戏结果/证书来源和权益转让备注都是可选上下文；两者都没有时，券仍可凭明确的发放方、领取方和权益条款成立。备注只是展示补充，不是平台对线下赌约的裁判或担保。

### 7.6 与现有模型的重复/冲突审计

| 概念 | 目标归属 | 与现有表/模型的关系 | 结论 |
| --- | --- | --- | --- |
| `PlayCard` / `Card` | 内容定义 | 现有合约里的 `gameCard/cardId` 是正式合约的玩法快照引用，不是游戏运行实例 | 不新增同名内容表；游戏内容版本和运行快照分开 |
| `Card Delivery` | 抽卡交付 | 只表示主持人当前取得的一张卡，不是房间、邀请或参与者记录 | 保留短期交付语义，不做分享/加入状态 |
| `GameCardInstance` | 游戏运行快照 | 不等同现有 `Agreement`，仅在主持人保存结果、证书或需要恢复时持久化 | 不创建 `game_sessions`；实例只冻结 L1/L2/Tool/卡面上下文 |
| `GameResultRecord` | 游戏结果域 | 与 `Agreement.winnerId/loserId/resultRecorderUserId` 语义相似，但只服务轻量游戏卡 | 正式合约复用 Agreement 结果字段；纯游戏结果只用 GameResultRecord，禁止双写 |
| `Certificate` | 结果传播视图 | 不是新的比赛资产；结果已有 `certificate_snapshot` 需求 | 默认作为结果的派生读模型/快照，不另建可变证书状态机 |
| `SettlementRequest` | 权益域 | 内容库没有对应表；它是发券动作，不是游戏结果 | 放在现有权益域，结果/证书、转让备注和关联合约都可为空 |
| `Coupon` | 统一权益资产 | 当前 `coupons.agreement_id` 必填，核销、赖皮券和 Flip 还假设 Agreement 存在 | 不新增 `GameCoupon`；先做权益域迁移设计，再决定统一 Coupon 来源模型 |
| `Flip` / `GraceWaiver` | 正式合约能力 | 当前均强绑定 Agreement/Coupon | 继续只服务正式合约；独立游戏结算不能直接复用，除非迁移后逐项补齐约束 |

审计结论：内容运营设计没有必要再增加 `Room`、`Join`、`GameCoupon`、`SharedCoupon`、`Claim` 或 `Settlement` 表。当前真正的冲突在权益域，不在 L0/L1/L2 分层；把 `agreement_id` 直接改成可空仍然是不完整的修复。

当前代码证据：

- `apps/api/src/db/schema.ts:55-75` 的 `agreements` 已经包含正式合约的玩法快照、参与者和结果字段。
- `apps/api/src/db/schema.ts:78-104` 的 `flips`、`151-176` 的 `grace_waivers` 都强依赖正式合约链路。
- `apps/api/src/db/schema.ts:106-130` 的 `coupons.agreement_id` 是非空外键；`packages/shared/src/index.ts:55-69` 也把 `agreementId` 写成必填。
- `apps/api/src/routes/games.ts:11-61` 仍是旧的 `Agreement(source=card)` 加入实现；它不是本次轻量游戏目标模型。
- `apps/api/src/routes/coupons.ts:46-49` 核销前无条件读取 Agreement 并检查其状态，因此不能只改数据库可空而不改核销、历史和权益状态逻辑。
- `docs/game-content-ops-schema.sql` 当前没有 `GameResultRecord`、`Certificate`、`Settlement`、`Coupon` 或 `Claim` 表，只有内容运营和行为数据；这应继续作为领域边界，而不是用重复表“补齐功能”。

## 8. 数据库未定项

当前业务代码的 `coupons.agreement_id` 是必填字段，`/games` 仍创建 `Agreement(source=card)` 并提供加入流程，Coupon 核销、赖皮券和 Flip 也都假设存在 Agreement。因此“游戏结果后独立发券”目前只能作为产品接口目标，不能直接当作已经成立的数据库设计。

开发前需要单独完成一次权益域迁移设计，至少比较：

1. 将 Coupon 来源泛化为正式 Agreement、GameResult/Certificate 或独立转让，并保留一张券一个 provider、一个 holder 的约束；所有来源上下文都可以为空，但发放方、领取方和权益条款必须完整。同步检查核销、赖皮券、翻盘和历史查询的所有 Agreement 假设。
2. 增加只负责待领取状态的权益发放层，领取后仍进入统一 Coupon；如果这样做会形成第二套资产状态，就停止采用。不能为游戏再建一套 Coupon/Claim 资产。

展示规则先固定为：有关联合约时展示合约上下文；无关联合约但有关联游戏结果/证书时展示结果上下文；前两者都没有且备注非空时展示权益转让备注；三者都没有时隐藏来源说明。三者是来源上下文，不是三种券。

在这项迁移完成前，内容运营 DDL 不应增加 Coupon、Claim、Settlement 或共享资产表。当前参考 SQL 只负责内容、卡片快照、曝光聚合和事件，不声明独立结算的最终表结构。
