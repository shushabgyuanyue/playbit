# Phase 3：规则推荐与数据分析

## 1. 目标

先用稳定、可解释、可调试的规则完成分发闭环，让用户行为能反哺 L1、L2 和场景判断。复杂模型放到 Phase 4。

## 2. 推荐请求

抽卡请求输入：

- 用户 ID 或匿名会话 ID。
- 参与人数。
- 当前入口和场景。
- 是否希望继续当前 L1。
- 是否需要支持结果记录或计分榜的玩法。
- 最近一次卡片和行为。
- 当前可用 Tool 和环境。

抽卡请求输出：

- `card_delivery_id` 和可验证卡片快照；需要持久化时再返回 `game_card_instance_id`。
- L1 和 L2 版本。
- 卡面展示快照。
- 推荐原因。
- 本次使用的策略版本。

## 3. 候选过滤

先做硬过滤，再做排序。候选必须满足：

1. L1 和 L2 处于可分发状态。
2. 当前人数、时长和场景匹配。
3. 当前用户没有处于内容冻结期。
4. 内容没有永久消耗。
5. 所需 Tool 和环境可用。
6. 最近没有重复相同 L1、L2 或变体。
7. 通过安全、适龄和版权规则。
8. 当前实验分组允许展示。

抽卡请求不根据彩头、发券或权益筛选候选。用户在游戏结束后选择记录结果时，再根据 L1 的 outcome_model 判断展示双人结果、多人计分榜或直接结束。推荐排序不应把“可记录结果”误当成“更值得推荐”。

如果过滤后候选不足，允许逐级放宽：先放宽相似度，再放宽 L1 冷却，最后使用经过审核的保底卡。永久消耗内容不能因为候选不足而重新展示。

## 4. 第一版排序

排序可以使用一个可解释的加权公式：

```text
score =
  scene_fit
  + user_l1_affinity
  + content_quality
  + freshness
  + diversity_bonus
  + exploration_weight
  - recent_repeat_penalty
  - fatigue_penalty
  - short_term_skip_penalty
```

各项分数都必须可在后台查看。第一版不追求精确预测，优先保证运营人员可以理解和修正。

收藏 L1 增加偏好分，但不绕过 L2 冻结和永久消耗。连续跳过某类场景只造成短期惩罚，经过时间衰减后恢复探索。

推荐的目标不是“最容易完成”，而是给当前场景找到一张最可能自然开局、玩得下去且不重复疲劳的卡。排序分成三层：

1. **硬约束**：审核、安全、人数、场景、内容复用、必需 Tool 和实验分组。
2. **体验排序**：场景适配、L1 偏好、内容质量、新鲜度、多样性和近期疲劳。
3. **受控探索**：给新 L1/L2、小样本内容和低曝光但合格的工具组合分配有限探索预算。

工具只参与硬约束和体验诊断，不作为单独的推荐内容。不能因为用户上次点开了计时器，就把下一张卡都推荐成计时玩法；应归因到对应 L1/L2 和场景。

每次推荐都保留可解释原因，例如“适合 3 人、预计 5 分钟、同类玩法已冷却、需要的计时器可用”。用户侧不展示内部得分，只在后台展示候选过滤和排序原因。

## 5. 行为事件

事件写入只做最少校验和幂等去重，不在同步请求中计算复杂指标。

核心事件：

```text
IMPRESSION       展示
REVEAL           展开或阅读
START            开始
SKIP             主动跳过
REDRAW           换卡
COMPLETE         完成
ABANDON          中途退出
REPLAY_SAME_L1   再玩同一玩法
SWITCH_L1        切换玩法
FAVORITE_L1      收藏玩法
UNFAVORITE_L1    取消收藏
RESULT_RECORDED 记录双人结果或完成结果
SCOREBOARD_RECORDED 记录多人分数和排名
CERTIFICATE_CREATED 生成结算或比赛证书
SHARE            分享证书或独立结算，不分享游戏卡
TOOL_OPENED      打开本局工具
TOOL_COMPLETED   工具完成一次有效操作
TOOL_SKIPPED     跳过可选工具
TOOL_ERROR       工具加载或运行失败
```

每条事件保存：事件 ID、客户端幂等 ID、匿名会话或用户 ID、时间、临时 Play Session ID、Card Delivery 或 Card Instance、L1、L2、事件类型和有限上下文。

不默认保存聊天原文、用户输入全文或不必要的个人信息。

## 6. 指标定义

### L1 指标

- 展示到开始率。
- 开始到完成率。
- 同 L1 再玩率。
- 切换 L1 率。
- 平均完成时长。
- 收藏率。
- 分享率。
- 真人试玩自然开局率。
- 真人试玩尴尬记录率。
- Tool 打开率、完成率和错误率；只用于判断运行摩擦，不直接替代游戏完成率。

### L2 指标

- 展示到开始率。
- 主动跳过率。
- 重抽率。
- 完成率。
- 中途退出率。
- 冷却后再次展示的完成率。
- 永久消耗速度。
- 内容敏感或异常反馈数量。
- Tool 使用可按 L2 下钻查看打开、完成和错误率，用于区分工具摩擦与具体内容问题。

高完成率不等于高质量。规则太简单、完成过于机械或卡片没有提供退出机会，都可能造成虚假的高完成率。

## 7. 性能边界

- 抽卡路径只能读发布内容、复用策略、分发策略和用户聚合状态。
- 不允许抽卡请求扫描 `game_events`。
- `game_events` 按月份分区，只追加写入。
- `user_l1_preferences` 和 `user_l2_exposures` 通过异步聚合或事务内增量更新。
- 报表读取 `l1_daily_metrics` 和 `l2_daily_metrics`。
- 原始事件使用 BRIN 时间索引和必要的用户、L1、L2索引。
- 客户端事件 ID 在有限窗口内去重，重复上报不能重复计数。
- 事件明细设置保留周期，历史数据进入分析存储或归档。

## 8. 后台分析页面

分析页面必须允许按以下维度切换：

- L1。
- L2。
- 场景。
- 人数。
- 新用户和回访用户。
- 版本。
- 推荐策略版本。
- 实验分组。

每个异常指标都能下钻到代表性 Card Delivery/Game Card Instance 和事件序列，但不展示隐私原文。

## 8.1 事件触发时机与统计口径

事件名称必须对应一个稳定的产品动作，不能由多个页面随意上报。建议口径如下：

- `IMPRESSION`：卡片完成首屏渲染并持续可见至少 500ms；预加载或接口返回不计入。
- `REVEAL`：用户完成首次展开/翻牌并看到完整可玩信息；没有展开动作的卡不计入。
- `START`：用户确认开始，且服务端将游戏局从 `CREATED` 变为 `STARTED`。
- `SKIP`：用户主动点击换卡或离开卡片，发生在开始前；自动轮播不计入。
- `REDRAW`：用户要求换一张具体卡；它不是换 L1，必须保留当前 L1 和目标 L2 的归因。
- `REPLAY_SAME_L1`：用户在结束或放弃后明确选择“再玩同一种玩法”；可以换 L2。
- `SWITCH_L1`：用户明确选择换玩法；不能把普通的下一张卡都记成切换 L1。
- `COMPLETE`：游戏规则达到结束条件并由服务端确认；关闭页面不算完成。
- `ABANDON`：已开始但未达到结束条件，且超过会话超时窗口或明确退出。

核心分母固定为去重后的卡片实例数或游戏局数，不能用事件总条数替代：

```text
展示到开始率 = distinct START card_instance_id / distinct IMPRESSION card_instance_id
开始到完成率 = distinct COMPLETE session_id / distinct START session_id
主动跳过率 = distinct SKIP card_instance_id / distinct IMPRESSION card_instance_id
同 L1 再玩率 = distinct REPLAY_SAME_L1 user_or_actor / distinct COMPLETE user_or_actor
```

报表必须标明时间窗口、去重键、归因窗口和是否包含匿名用户。推荐归因默认绑定到生成该卡片实例的策略版本，不根据后来重新计算的策略回填历史。

## 8.2 L1/L2 状态和推荐策略的优先级

候选判断顺序固定为：安全与年龄限制 → 内容和版本已发布 → L2 供应量/隔离状态 → 场景和人数匹配 → L1 冷却 → L2 冷却/永久消耗 → 实验分组 → 分数排序。任何降级都不能越过安全限制、版本审核或永久消耗。

同一实体的分发策略按作用域从具体到通用生效：

```text
L2 + 场景 > L2 > L1 + 场景 > L1 > 全局
```

同一作用域只允许一条 `is_active = true` 的策略；需要变更时在一个事务中关闭旧策略、写入新策略和审计记录。作用域优先级高于 `priority`，`priority` 只解决同一作用域内的排序。

## 8.3 推荐失败和空候选体验

推荐接口必须区分“没有合适候选”和“服务异常”。没有候选时给用户可理解的重试入口，不强行重复永久消耗内容；服务异常时先使用审核过的基础候选缓存，缓存也不可用才展示可恢复的错误状态。离线场景只允许继续已经生成的卡片或游戏局，不在本地伪造新的推荐结果。

运营端需要看到每次空候选的原因计数：无发布内容、全部冷却、全部耗尽、场景不匹配、工具不可用、实验过滤或系统超时。否则只能看到“抽不到”，无法判断是内容供给问题还是算法问题。

## 8.4 分析主库与分析副本

线上主库只承载内容、聚合状态、卡片实例和事件追加写入。后台的日期、场景、人数、用户 cohort、版本、策略版本、实验编码和实验分组下钻使用 `recommendation_daily_slices` 或分析副本，不允许管理端直接扫描 `game_events`。

日报基础表适合趋势和推荐读取，多维切片适合运营分析；两者都必须保留 L1 与 L2 维度，避免只看 L1 导致内容质量问题被玩法平均值掩盖。切片维度需要设置白名单和保留周期，禁止把昵称、聊天原文或任意 JSON 字段变成无限增长的索引维度。

## 9. Phase 3 验收

- 抽卡能解释候选被过滤和排序的原因。
- 用户收藏 L1 后能影响后续排序。
- 同一 L1 再玩和切换 L1 能分别统计。
- L2 永久消耗和冷却规则有效。
- 连续跳过会产生短期影响，且会衰减。
- 行为重复上报不会重复计数。
- 抽卡性能不随事件明细量线性变慢。
- 后台可以查看 L1 和 L2 分层指标。
- 相同事件在重复上报后不会改变分子或分母。
- 分析页面能按场景、人数、用户 cohort、版本、策略版本和实验组下钻。
- 空候选能够区分供给不足、冷却、隔离、匹配失败和系统超时。
