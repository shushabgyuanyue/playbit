# 游戏结果与独立权益发放边界

状态：产品边界已落地；继续作为游戏结果与独立权益域的执行依据

## 1. 产品判断

游戏卡的核心是“马上玩完并把结果算清楚”。下注、加注和彩头由参与者在线下自行约定，Playbit 不在游戏开始前锁定权益，也不判断线下约定是否真实。

游戏结束后，Playbit 提供三条可以独立结束的动作：

1. 记录双人胜负，或记录多人分数和排名。
2. 主持人根据结果生成并分享结果/比赛证书。
3. 履约方单独发起结算，向指定胜方发放一张独立权益券。

第二步和第三步互不阻塞。其他参与者不需要进入原游戏卡页面；主持人可以只分享证书，履约方也可以从独立入口发起结算。没有发券时，结果仍然可以记录和分享。

## 2. 游戏结果记录

结果记录不是房间，也不是完整的在线对局。它只保存生成证书和归因所需的最小快照。

### 2.1 最小字段

```text
GameResultRecord
  id
  card_instance_id
  l1_version_id
  l2_version_id
  result_model                 -- SELF_REPORTED_WINNER / RANKED_RESULT / ...
  recorder_user_id             -- 谁提交了结果
  status                       -- DRAFT / RECORDED / CANCELLED
  result_snapshot              -- 结果、分数、排名、文字快照
  certificate_snapshot         -- 主持人证书渲染所需的冻结数据，可为空
  created_at / confirmed_at
```

参与者是结果记录的子项，不是房间成员：

```text
GameResultParticipant
  result_id
  user_id nullable              -- 未登录时为空
  display_name_snapshot         -- 证书使用的昵称快照
  role                          -- WINNER / LOSER / PARTICIPANT
  score nullable
  rank nullable
```

双人结果至少要有一名 WINNER 和一名 LOSER，或明确记录 DRAW / NO_RESULT。多人结果可以有多个 WINNER、LOSER 或普通参与者。平台只记录提交结果，不把结果当作裁判事实。

## 3. 证书规则

- 双人结果生成结果证书，展示胜者、对手、玩法、日期和“由主持人登记”的状态。
- 多人结果生成比赛证书，展示排名和参与者；是否有线下奖励不写成平台承诺。
- `CERTIFICATE_CREATED` 只表示证书已生成，不表示权益已发放。
- 证书必须引用冻结的卡片和结果快照，后续内容版本修改不影响历史证书。
- 主持人登记完成后即可生成和分享证书，证书明确“主持人登记”。独立结算可以不依赖证书；如果引用游戏结果，至少要有主持人的 `RECORDED` 结果快照。

首期不要求其他参与者打开或回到游戏卡确认。多人由主持人/登记人提交排名，证书明确登记人身份；双方确认只属于正式 Agreement 流程，不进入轻量游戏结果流程。

## 4. 独立权益券

权益券的语义等同于一笔从输方到胜方的独立承诺：

```text
provider / issuer  ->  独立 Coupon  ->  holder
```

一张券只有一个履约方和一个领取方，不存在共享券、多人共同持有或排名绑定一张券的情况。

### 4.1 发放前提

- 发券人必须是真实的履约方。若结算引用了游戏结果，结果至少已经 `RECORDED`；没有结果也可以从独立入口发起。
- 游戏结果里的 LOSER 通常是履约方，但平台不替用户判断或强制映射。主持人如果也是输方，可以直接发券；主持人不是履约方时只分享证书，不代替他人发券。
- 发券人主动填写权益条款并确认发放。
- 平台生成唯一的一次性领取链接；未登录的胜方领取时再绑定账号。
- 发券动作不改变原游戏结果，也不自动创建 Agreement。

结算来源可以选择以下任意上下文，也可以全部不关联：

1. 正式合约上下文：关联 `Agreement`；
2. 游戏上下文：关联已 `RECORDED` 的 `GameResultRecord` 或其证书；
3. 独立转让备注：不关联合约和游戏结果时，可填写权益转让备注；备注为空也不影响发券。

`agreement_id`、游戏结果/证书引用和 `transfer_note` 在概念上都可以为空；券仍必须有明确的 provider、holder 和权益条款。这里的“可空”是统一权益模型的目标，不代表当前代码已经支持；当前数据库仍要求 `coupons.agreement_id`。

### 4.2 建议状态

```text
ISSUED → CLAIMED → ACTIVE → FULFILLED
   │         │         └────→ WAIVED / EXPIRED
   └──────→ REVOKED
```

`ISSUED` 是输方已经发出但胜方尚未领取；`CLAIMED` 是链接已绑定领取人；`ACTIVE` 是胜方已领取并同意；`FULFILLED`、`WAIVED` 和 `EXPIRED` 是后续权益结果。重复扫码必须返回同一张券，不能创建第二张。

### 4.3 多人发放

多人排名不自动生成权益。用户在结果页逐张发放：

```text
输方 A → 胜方 1：Coupon A-1
输方 A → 胜方 2：Coupon A-2
输方 B → 胜方 1：Coupon B-1
```

每次发放单独确认、单独领取、单独履约。若用户只想线下兑现，直接结束于证书，不显示发券操作。

## 5. 页面动作

游戏结束页按结果模型显示：

- 双人：`记录本局结果` → `生成结算证书`。
- 多人：`打开计分榜` → `确认排名` → `生成比赛证书`。
- 证书页：主持人看到证书和分享动作；如果当前账号是履约方，可以进入结算，但不要求胜方回到原游戏卡。
- 独立结算入口：履约方选择一个胜方，可选关联结果/证书和权益转让备注，也可以全部留空，再确认发放一张权益券。不得出现“共享给所有人”或“合并权益”。
- 胜方打开二维码：查看条款 → `领取并同意` → 绑定到本人卡券中心。

游戏卡前置区域只保留一条说明：

> 彩头由双方自行约定，Playbit 负责记录结果并提供证书；结算权益由输方自愿发放。

这句话是边界提示，不是风险弹窗，也不应抢走“开始游戏”的注意力。结算说明可以在独立发券页面再次出现，不需要留在游戏卡主流程里。

## 6. 系统归属

- 内容运营库：L0、L1、L2、Tool、Card Delivery、Game Card Instance、行为事件和推荐聚合。
- Game Result 领域：结果记录、参与者快照、计分榜、排名和证书快照。
- 现有 Agreement/Coupon/Flip 领域：正式签约权益、独立结算券、领取、履约和翻盘。

内容系统可以保存 `game_result_id` 作为归因引用，但不复制 Coupon、Claim、Settlement 或 Room 表。独立结算所需的 Coupon 来源扩展仍是待定数据库决策：当前实现要求 `coupons.agreement_id` 必填，且核销、赖皮券和翻盘都依赖 Agreement。开发前必须先完成权益域迁移设计和回归测试，再决定是泛化 Coupon 的来源类型，还是增加一个只负责待领取状态的权益发放层；不能在内容库里机械增加第二套券表。独立结算不要求存在证书，也不要求收券人进入游戏卡；若没有游戏来源且备注为空，则不展示来源说明。
