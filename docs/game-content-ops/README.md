## 产品边界

用户只看到一张可以立即开始的游戏卡。L0、L1、L2、Tool、推荐分数和冻结次数属于后台语言，不出现在用户界面。

Playbit 当前不引入房间大厅、强制注册、内置 AI 裁判、真实资金和复杂游戏进度。匿名用户可以抽卡和开始游戏，不为普通轻玩创建持久化游戏局；收藏、持续推荐、结果证书、发券和历史记录等持久化能力再要求登录。游戏卡负责轻量游玩和主持人证书；独立结算可以从证书或其他独立入口发起，正式 Agreement/Coupon/Flip 仍由合约产品负责。

## 四阶段依赖

```text
Phase 1 数据与状态基础
        ↓
Phase 2 管理端研发与审核闭环
        ↓
Phase 3 规则分发与统计闭环
        ↓
Phase 4 Agent 协作与智能推荐
```

Phase 3 可以在 Phase 2 的少量人工内容上运行。Phase 4 不应在没有稳定事件、版本和审核记录的情况下提前开发复杂模型。

## 统一术语

- **L0**：核心互动机制分类，只用于研究和分析。
- **L1**：可重复玩的玩法骨架，定义行动、信息、控制和结束条件。
- **L2**：某一次具体游玩的内容包。
- **Tool**：计时、揭晓、私密查看、排序等运行能力。
- **Game Card Instance**：一次抽卡冻结后的用户可玩卡片实例。
- **Play Session ID**：用于事件归因的临时游玩标识，不代表房间、参与者关系或权益状态。
- **Exposure**：用户与某条内容的展示、开始、完成和消耗状态。

## 开发规则

1. 已发布的 L1/L2 不原地修改，发布必须创建新版本。
2. 游戏局保存实际使用的版本，历史内容必须可还原。
3. 行为明细只追加，线上抽卡读取聚合状态，不扫描事件表。
4. Agent 只能创建提案，人工拥有发布权。
5. 推荐先做可解释的规则排序，再接模型和 Bandit。
6. 管理员调整分发策略必须有范围、理由、审计和回滚。
7. 内容状态、审核状态、运行状态和用户曝光状态不能混用。

## 总体验收

完成四阶段后，系统应能够：

- 从原始样本建立一个 L1 和多个 L2。
- 经过 Agent 提案和人工审核后发布一个版本。
- 生成用户可以立即玩的 Game Card Instance。
- 按用户、内容和场景执行冻结与消耗规则。
- 记录并聚合行为数据，不因事件量增长拖慢抽卡。
- 通过管理端查看内容质量、推荐表现和人工调整记录。
- 在保留人工审核的前提下，让 Agent 和推荐算法持续扩大有效牌库。
- 普通轻玩、多人排名和双人结果分别走轻玩、证书和可选的独立权益发放路径；不自动创建共享券，也不把游戏卡伪造成 Agreement/Coupon。

## 可重复验收

本地启动 Web、API 和 Chrome CDP 后，可从仓库根目录运行：

```bash
pnpm verify:browser
```

该命令会分别验证 `/studio` 的内容草稿流程，以及 390×844 移动视口下的首页、游戏卡、复用工具和结果记录流程，并将截图写入 `artifacts/verification/`。它只验证原型行为，不代表 PostgreSQL 持久化、权限和生产并发门槛已经完成。
