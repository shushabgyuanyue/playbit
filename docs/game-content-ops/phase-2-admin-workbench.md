# Phase 2：PC 管理端最小闭环

## 1. 目标

让内容团队能够在 PC 端完成：原始样本整理、L1 规则编辑、L2 内容维护、卡片预览、人工审核、真人试玩记录和小流量发布。

本阶段的后台优先服务内容工作流，不追求复杂 BI，也不把所有数据库字段直接堆在页面上。

## 2. 页面结构

左侧固定导航只保留五个工作区：

1. 总览。
2. 内容库：原始样本、L1 玩法、L2 内容和 Agent 提案。
3. 游戏卡实验室：真实卡面、开局流程和测试卡。
4. 审核与试玩：审核队列、真人试玩和发布决定。
5. 分发与分析：冷却策略、探索比例、质量指标和推荐表现。

标签与状态作为系统设置，不单独占一个一级菜单。Agent 任务作为内容库和审核队列中的工作视图，不单独制造一套平行导航。

顶部显示当前环境、当前用户、最近操作和全局搜索。所有列表页面都支持按状态、更新时间、负责人和来源筛选。

## 3. 总览页

总览页只展示帮助团队做决定的指标：

- 原始样本总数。
- L1 总数和各生命周期数量。
- 待审核提案。
- 待试玩 L1。
- 已发布 L1/L2。
- 最近 7 天抽卡、开始、完成和重抽趋势。
- 异常内容：高跳过、高退出、低开始率、重复过快。
- 最近发布和最近暂停的内容。

总览数字都要能点击进入明细。不要做只展示数字的大型装饰卡片。

## 4. 原始样本库

### 列表字段

- 样本名称。
- 来源类型、地区和作品。
- 证据级别。
- 原始状态。
- 关联 L1 数量。
- 编辑优先级。
- 最近更新时间。

### 详情能力

- 查看原始规则和来源链接。
- 查看核心互动、信息结构和控制结构。
- 查看 L0 假设。
- 查看相似样本。
- 建立或修改 `raw_l1_rel`。
- 转为 Agent 分析任务。
- 标记合并、观察或不采用。

原始样本详情不能只展示 Agent 总结，必须保留原始规则和来源证据。

## 5. L1 工作台

采用“左侧编辑、右侧预览”的双栏布局。

左侧分为：

- 基本信息：名称、人数、时长、道具、移动程度。
- 结果模型：无胜负、双人结果登记、多人排名或共同完成；是否支持结果记录、是否可生成比赛证书、是否需要主持人。
- 规则：短规则、详细规则、完成条件、失败条件。
- 信息结构：公开、私密、逐步揭示、同步揭晓等。
- 控制结构：轮流、同时、主持、随机等。
- 场景适配。
- L0 关系。
- 当前 L1 版本的 Tool 关系。
- 版本和编辑说明。

Tool 关系必须显示“必需/可选”、默认配置、当前发布版本、运行环境和不可用时的降级方式。一个 L1 可以没有 Tool 关系；需要工具时只从目录复用已有版本，不新建卡片专属工具。关系绑定具体 L1 版本；编辑人员可以在草稿预览中切换工具状态，但不能用任意 JSON 绕过 Tool 的配置约束，也不能修改已发布版本的工具关系。

右侧分为：

- 用户游戏卡预览。
- 参与者视角预览。
- 选定 L2 后的真实内容预览。
- 开局、进行中、揭晓和结束状态。
- 多人排名时的计分板和比赛证书预览。
- 手机宽度预览。

保存和发布必须分开。保存只生成草稿或新版本，发布才进入分发候选。

## 6. L2 内容池

L2 列表以 L1 为主筛选，不做一个把所有题目混在一起的内容大表。

详情页面必须支持：

- 结构化字段编辑。
- 内容预览。
- 敏感度和适龄标签。
- 来源和创作方式。
- 质量等级。
- 单条内容审核。
- 批量导入草稿。
- 冻结时间、轮数和最大展示次数。
- 永久消耗开关。
- 版本和退役记录。

结构化内容包要按 L1 的 `content_type` 渲染，不允许后台只编辑一段不可验证的大文本。

## 7. 游戏卡实验室

这是管理端最重要的体验页面。它需要让编辑人员像用户一样拿到一张卡，而不是只看数据库字段。

操作流程：

1. 选择一个已发布或草稿 L1。
2. 选择一个 L2 或生成测试 L2。
3. 加载 Tool 配置。
4. 预览卡面。
5. 运行一遍开局、进行中、揭晓和完成流程。
6. 记录问题或直接发起试玩。

实验室里的测试局不能进入真实推荐数据，除非明确标记为真人试玩。

### 7.1 Tool 目录与预检

Tool 目录不是用户工具商城，而是内容团队管理运行能力的目录。每个 Tool 需要维护：

- 用户可见名称和内部运行标识。
- 发布版本、配置 Schema、支持的平台和输入方式。
- 必需/可选关系及默认配置。
- 无法加载时的降级行为。
- 最近被哪些 L1 使用、错误率和完成率。

L1 发布前必须通过 Tool 预检：配置合法、必需工具有可用运行时、移动端一屏可操作、工具入口不遮挡规则、超时和离线行为明确。没有 Tool 的 L1 直接跳过工具预检；工具改版产生新版本，不直接覆盖正在使用的版本。

## 8. 审核队列

审核列表按“需要做决定”排序，不按 Agent 完成时间排序。

每个提案展示：

- 提案类型和目标对象。
- 原版本和新版本的字段差异。
- 来源证据。
- Agent 变更理由。
- 相似 L1。
- 风险提示。
- 试玩建议。
- 最近表现。

审核动作：

```text
通过 → 进入下一个状态
观察 → 保留但暂不进入主流程
试玩 → 创建试玩任务
合并 → 关联到现有 L1
淘汰 → 记录原因并停止流转
暂停 → 下线但保留恢复可能
```

人工决定必须填写原因。原因是研发资产，不是审计形式。

## 9. 试玩页面

试玩记录至少包括：人数、关系、地点类型、是否坐着、是否需要道具、是否自然开始、是否规则讲清、哪里尴尬、是否想再来。

不把试玩压缩成一个 1 到 10 分。数值可以辅助统计，但自由观察必须保留。

## 10. 分发策略页

管理员可调整：

- 基础权重。
- 探索权重。
- 场景适配。
- 冷却轮数。
- 冷却天数。
- 最大展示次数。
- 最大游玩次数。
- 是否永久消耗。
- 生效时间。

调整必须显示旧值、新值、操作人、原因和回滚入口。输入框设置业务上下限，防止把冷却设为负数或把单条内容无限曝光。

## 10.1 权限与服务端校验

管理端角色不能只存在于前端菜单。服务端必须根据 `admin_user_roles` 校验权限，前端隐藏菜单只用于减少误操作。

建议最小角色：

- 内容研究员：维护原始样本、L0 关系和 Agent 任务，不得发布。
- 内容编辑：创建 L1/L2 草稿、发起试玩和提交审核，不得自己批准自己的提案。
- 审核员：审核具体版本、暂停或隔离内容，可以发布已通过审核的版本。
- 运营管理员：调整分发和复用策略、控制小流量发布，可以回滚策略。
- 只读分析员：查看指标、样本和审计记录，不得修改内容或策略。

所有写操作都要在服务端再次检查角色、目标实体状态和版本状态。发布、暂停、隔离、策略调整和权限变更必须写入审计日志；审计日志不可由普通管理端操作删除。

## 10.2 内容供应量与隔离

L2 详情页必须同时展示“可分发量、已分发量、剩余量、耗尽预警阈值、最近一次分发时间”。剩余量接近阈值时进入运营预警，达到上限时自动停止进入候选池。

“隔离”使用独立的 `QUARANTINED` 状态，原因必填，常见原因包括用户举报、敏感风险、规则漏洞、版本回滚和数据异常。隔离内容不再进入新抽卡，但已经生成的卡片实例仍按版本快照完成；解除隔离必须重新审核，不允许只改回状态绕过审核。

手动降权必须填写原因并记录旧值、新值和生效范围。运营人员不能通过把权重设为零来替代暂停或隔离，因为这会让内容看似发布、实际无法解释。

## 11. Phase 2 验收

- 编辑人员可以从原始样本进入 L1 工作台。
- L1 工作台能看到真实用户卡片预览。
- L2 可以按结构化字段编辑和审核。
- Agent 提案可以查看差异并进入人工审核。
- 试玩记录不会污染正式推荐数据。
- 发布、暂停、退役和恢复都有明确状态。
- 分发策略修改有审计和回滚。
- 不同管理角色在服务端拥有不同的写权限，前端隐藏菜单不能绕过校验。
- L2 能显示供应量和耗尽预警，并能以带原因的隔离状态退出候选池。
- L1 发布前能完成 Tool 配置预检，工具版本和降级方式清楚可见。
- 手动降权、隔离和解除隔离都能查看旧值、新值、操作人和原因。
