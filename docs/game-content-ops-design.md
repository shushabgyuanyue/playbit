# Playbit 游戏卡智能研发与分发系统

版本：v0.1
状态：用户端、管理端原型与内存 API 已落地；PostgreSQL 生产迁移按独立数据库环境执行
适用对象：产品、前端、API、数据、Agent 开发人员

## 1. 文档目标

本文档定义 Playbit 游戏卡从内容采矿、Agent 提案、人工审核、真人试玩、发布分发到行为反馈的完整系统。用户侧保持“抽到一张卡，马上开始玩”的简单体验，后台承担内容研发、复用控制和推荐复杂性。

本系统不把 L0、L1、L2 暴露给用户。它们是研发语言和数据边界。

## 2. 产品目标

Playbit 应持续给用户提供满足以下条件的游戏卡：

- 打开后可以直接开始，不依赖账号、房间或复杂设置。
- 规则短、容易解释，第一次玩也不尴尬。
- 适合碎片社交，通常在几分钟内完成一轮。
- 内容有新鲜度，已经消耗的内容按规则降低或停止展示。
- 卡片质量由人工把关，推荐由用户行为和场景共同驱动。

“极致好玩”是产品目标，不是推荐算法可以直接保证的承诺。系统必须把它拆成自然开局、完成、再玩、分享、低尴尬和低跳过等可验证指标。

## 3. 不在本系统范围内

- 不做实时语音或视频裁判。
- 不做真实资金托管、充值、提现和排行榜。
- 不要求用户先建房间或等待大厅。
- 不把 AI 直接作为用户必须使用的 Playbit 内置能力。
- 不用自动评分直接决定内容上线。
- 不把 L0 做成用户可浏览的玩法分类入口。

## 4. 核心对象

### 4.1 L0：机制分类

L0 描述“为什么这类玩法可能成立”，用于研究、聚类、推荐解释和发现机制空白。

当前分类包括约束冲突、受限检索、累积负荷、未知信息推断、心智博弈、自我揭示与社会判断、联想重构、共创接力、感知动作博弈，以及仍需观察的同步协调/反同步和局面策略。

L0 不参与用户抽卡，也不直接生成用户卡片。

### 4.2 L1：可重复运行的玩法骨架

L1 是用户可以反复玩的玩法类型，例如海龟汤、三句话一句假、只能说三个字、盲排和猜人名。

L1 必须定义：

- 参与人数和参与者角色。
- 行动顺序和控制权。
- 信息如何分布、隐藏和揭晓。
- 一轮如何开始、继续和结束。
- 胜负或完成条件。
- 失败、超时和放弃处理。
- 所需 Tool。
- 适合的场景、时长和移动限制。
- 结果模型：无胜负、双人结果确认、多人排名或共同完成。
- 是否支持结果记录、计分榜和比赛证书。
- 是否需要主持人。

结果模型只决定游戏结束时能记录什么，不决定用户是否要设置彩头。双人卡可以由主持人登记结果，多人卡可以记录分数和排名；游戏卡流程不自动创建 Agreement、Coupon 或 Flip。

### 4.3 L2：具体内容包

L2 是某一次实际游玩的内容，不限于一段文本。海龟汤 L2 应包含谜面、真相、提示、主持人允许回答的范围和揭晓文案。盲排 L2 可以包含待排序项目和排序约束。现实环境类玩法可以声明由现场生成，不固定保存内容。

L2 可以独立审核、冻结、消耗、冷却和退役。

### 4.4 Tool：可复用运行能力

Tool 是玩法所需的辅助能力，例如计数器、计时器、私密查看、揭晓、随机词、投票、记分牌、排序和尺度选择。Tool 不是 L3，不是用户侧的玩法分类，也不单独进入抽卡池；它是由多个 L1 复用的稳定运行组件。

Tool 是共享能力目录，不是每张卡都要创建的配套内容。一个 L1 版本可以不关联任何 Tool，也可以按需关联一个或多个已有 Tool；L2 只引用 L1 的 Tool 关系，不复制工具实现。每个 Tool 必须有版本、运行标识、配置约束、输入/输出语义、可用环境和降级方式。`REQUIRED` Tool 不可用时，关联它的卡片不能进入候选；`OPTIONAL` Tool 不可用时，必须能隐藏或回退到主持人口头玩法，不得让游戏卡进入半可用状态。Tool 关系绑定具体 L1 版本，发布后的 Tool 版本和 L1/Tool 关系都不可原地改变，Game Card Instance 保存实际使用的 Tool 版本和配置快照。

工具箱只在游戏卡内按需出现：主持人点击“工具”后看到本局所需和可选工具，不先进入工具市场或工具列表。必需工具在开局区域就有明确入口，可选工具收进轻量工具栏，不遮挡规则和卡面。工具打开后优先使用卡片内嵌的小面板或底部抽屉，保持当前游戏上下文，不跳转到独立页面；计时器、计数器和记分牌都提供一键开始/暂停、加减、重置等高频操作，并保留清楚的按压反馈和状态显示。它们的状态默认只属于当前本地游玩，不形成全局积分、赛季或用户资产；工具事件只用于诊断“工具是否降低了开局和完成摩擦”。

### 4.5 用户游戏卡

用户看到的是完整游戏卡，不看到 L0、L1、L2。一次抽卡先形成一个短期的 Card Delivery；只有主持人保存结果/证书、登录后保留历史或需要服务端恢复等持久化边界，才将它固化为 Game Card Instance。游戏卡本身不进入分享、邀请或扫码流程：主持人自己看卡，参与者在线下同步规则和内容。

```text
GameCardInstance = L1 玩法版本 + L2 内容版本 + Tool 配置 + 卡面文案 + 分发上下文
```

实例一旦进入游戏，后台后续修改内容不能影响这一局。匿名用户直接玩卡不创建 guest user、Agreement 或持久化游戏局；短期交付可以由签名快照、客户端状态和有限缓存保证重取。

Card Delivery 不是新的内容分层，也不是 Agreement。它只是把已发布的 L1/L2/Tool 组合成用户当前看到的卡。L0/L1/L2/Tool 仍然是唯一的内容研发边界。

### 4.6 未来多人模式的边界

多人模式暂不进入首期，但 L1 必须保留参与者角色、人数范围、行动顺序和结束条件。未来仍优先支持主持人带玩，但卡片只在主持人设备上运行：

~~~text
主持人抽到一张卡
  → 主持人查看规则、口头推进、揭晓和结束
  → 参与者不需要进入游戏卡，也不需要加入 Playbit
  → 主持人可选记录结果、分数和排名并生成、分享证书
  → 履约方可从独立入口发起结算，不要求参与者回到游戏卡
~~~

这不是房间系统：没有大厅、准备阶段、座位管理、卡片分享或强制加入。大家可以只在线下玩游戏而完全不进入 Playbit 的记录流程。彩头和权益设置由参与者自己约定，平台只记录主持人主动提交的结果，不判断谁应该赢，也不代替参与者发放权益。

证书和结算权益是两条独立链路。主持人可以生成并分享证书；履约方也可以从独立入口向指定胜方发放一张独立权益券，不要求胜方进入原游戏卡页面。每张券只有一个 issuer/provider 和一个 holder，不存在共享券；胜方扫码领取并同意后绑定账号并生效。未发券时仍可生成证书。正式合约、Coupon 和 Flip 仍属于合约产品，游戏卡不自动进入正式签约，也不在内容系统另造房间、下注账本或结算资产模型。

结果模式要在 L1 上明确分流：

- NO_WINNER / SHARED_COMPLETION：只玩和完成，可不记录结果。
- SELF_REPORTED_WINNER：双人结束时由主持人登记结果，可生成结算证书；对方确认是可选的，输方愿意时再单独发一张券给胜方。
- RANKED_RESULT：多人使用可选计分板和排名，可生成比赛证书；发券由输方在结果后逐张决定。

多人排名中的“前几名赢”只是被记录的游戏结果，不自动等于平台资产分配。每张实际发出的券都必须明确 issuer/provider 和 holder；Playbit 不替参与者决定发给谁，也不把多人排名折算成共享权益。

## 5. 用户侧体验

### 5.1 卡面内容

用户卡片只展示：

- 玩法标题。
- 一句 Hook。
- 人数和预计时长。
- 极简规则。
- 胜负或结束方式。
- 主按钮“就玩这张”。
- 次按钮“换一张”。
- 轻入口“收藏玩法”或“再玩这一类”。

用户不需要理解内容来源、机制分类、推荐分数、冻结次数和版本号。

### 5.2 继续玩同一类玩法

“再玩一局”保持 L1 不变，重新抽取或生成 L2；“换一张”允许切换 L1。后台分别记录 `replay_same_l1` 和 `switch_l1`，推荐系统不能把两者混为一个行为。

用户收藏的是 L1，不是某一张已经玩过的 L2。收藏代表“我喜欢这种互动方式”，不代表重复展示同一内容。

### 5.3 内容复用规则

系统必须区分“展示过”和“玩过”：

- 只展示但没有开始：短暂冷却。
- 点击开始但中途退出：中等冷却。
- 完成过一次：按内容类型决定再次展示或永久消耗。
- 主动跳过：形成短期弱负反馈，不立即永久拉黑。
- 收藏 L1：提高该 L1 的推荐倾向，但仍遵守具体 L2 的消耗策略。

典型策略：海龟汤具体故事玩过后永久不展示；猜人名具体内容冷却 30 轮；只能说三个字保持 L1 推荐但更换 L2；现实环境玩法每次重新取现场内容。

## 6. 内容研发工作流

```text
采矿 → 机制分析 → 去重归并 → Agent 提案 → 人工审核 → 真人试玩
→ 小流量发布 → 行为观察 → 调整、降权或退役
```

Agent 可以查找来源、拆解规则、聚类重复、提出 L1、生成 L2 初稿和分析低表现原因。Agent 不能直接发布、覆盖正式规则、删除历史内容或调整全局推荐权重。

每份 Agent 提案必须携带来源、父级样本或 L1、变更内容、变更理由、可能的尴尬点、适用场景和试玩建议。

内容状态：

```text
DRAFT → AGENT_PROPOSED → REVIEW → PLAYTEST → APPROVED
→ LIMITED_RELEASE → PUBLISHED → PAUSED / RETIRED
```

补充状态：`MERGED` 表示被更优 L1 吸收，`REJECTED` 表示当前不进入 Playbit。待定、淘汰、合并、暂停和退役必须区分，便于后续复盘。

人工审核至少判断：机制是否成立、能否自然开局、是否尴尬、卡面是否讲得清、是否适合碎片场景、是否存在安全或版权风险，以及是否值得占用牌库曝光。

## 7. PC 管理端

管理端面向内容编辑、产品、数据和管理员，优先服务四个动作：找到玩法、做出可试玩卡、作出审核决定、调整分发。

### 7.1 导航

管理端只保留五个一级工作区：

- 总览：内容规模、待审核、试玩中、发布状态和异常指标。
- 内容库：原始样本、L1、L2、来源证据、Agent 提案和版本关系。
- 游戏卡实验室：组合 L1/L2/Tool，预览真实卡面和开局流程。
- 审核与试玩：提案差异、审核队列、真人试玩和发布决定。
- 分发与分析：冻结、展示上限、冷却、探索比例、场景适配和行为表现。

标签与状态属于系统设置；Agent 任务作为内容库和审核队列里的工作视图，不单独制造平行导航。

### 7.2 L1 工作台

左侧编辑规则和研发字段，右侧固定显示用户真实卡面预览。必须能切换：

- 用户卡面。
- 发起者视角。
- 参与者视角。
- L2 内容替换。
- Tool 开关和配置。
- 手机尺寸预览。
- 开局、揭晓和结束流程。

页面要显示来源样本、相似 L1、Agent 提案、当前版本、审核结论、试玩记录和近期表现。字段保存与发布分开，发布必须创建不可变版本。

### 7.3 审核队列

审核卡片需要并列展示原版本和提案版本，突出规则变化，而不是只展示一段 Agent 总结。人工可以选择通过、暂定、进入试玩、合并、淘汰、暂停，并必须填写决定理由。

### 7.4 分发策略

管理员可调整冻结轮数、冻结天数、最大展示次数、最大游玩次数、探索权重和场景适配。所有调整记录操作者、原因、生效时间、旧值和新值，并有上限校验和回滚能力。

## 8. 推荐系统

第一阶段采用“候选过滤 + 规则排序”，不直接训练复杂模型。

候选过滤条件：

- 人数、场景、时长和移动限制匹配。
- L1/L2 已发布且未暂停。
- 当前用户未处于冻结期。
- 内容未永久消耗。
- 近期没有重复的 L1、L2 或同一变体。
- 所需 Tool 和环境可用。
- 通过安全、版权和年龄规则。

排序信号：

```text
场景适配 + L1 偏好 + 新鲜度 + 内容质量 + 多样性
+ 最近完成反馈 + 少量探索
- 重复度 - 疲劳度 - 短期跳过惩罚
```

跳过是弱负反馈。连续跳过同一类场景时，先影响当前会话和短期画像，不立即形成永久偏好结论。推荐结果需要保存简短的推荐原因，便于后台解释和纠错。

当数据量足够后，再引入上下文 Bandit 或其他智能排序。新内容必须保留探索配额，不能因为没有历史数据而永远没有曝光。

## 9. 行为事件和指标

事件至少包括：

```text
IMPRESSION       展示
REVEAL           展开或认真阅读
START            开始游戏
SKIP             主动跳过
REDRAW           换卡
COMPLETE         完成
REPLAY_SAME_L1   再玩同一玩法
SWITCH_L1        切换玩法
FAVORITE_L1      收藏玩法
UNFAVORITE_L1    取消收藏
SHARE            分享证书或独立结算，不分享游戏卡
RESULT_RECORDED  记录双人结果或完成结果
SCOREBOARD_RECORDED 记录多人分数和排名
CERTIFICATE_CREATED 生成结算或比赛证书
ABANDON          中途退出
```

L1 指标重点是自然开始率、完成率、同 L1 再玩率、切换率和试玩尴尬记录。L2 指标重点是展示后开始率、重抽率、完成率、重复疲劳和冷却后的复用表现。

不要用单一热门分数决定上线。高完成可能代表规则过于简单，高跳过也可能是场景不对或卡面没有讲清楚。

## 10. 性能设计要求

内容实体和高频行为事件必须分开。抽卡和卡面读取不能扫描行为明细表。

- 卡片读取只访问已发布的 L1 版本、可用 L2 内容和复用策略。
- 用户内容状态读取使用 `user_l1_exposures` 和 `user_l2_exposures` 的聚合行，不现场聚合全部历史事件。
- 行为事件使用按月分区的追加表，写入路径不做复杂关联和同步统计。
- 推荐所需的用户画像、L1 偏好和 L2 暴露状态使用异步聚合任务更新。
- 后台报表读取汇总表或分析副本，不直接查询线上事件明细。
- 热数据保留近期窗口，历史事件按月归档或压缩。
- 高并发写入使用客户端事件 ID 去重，事件入库必须幂等。
- 事件明细默认不建立过多外键和级联删除，避免高频写入被业务实体锁住。

推荐请求的目标是一次查询拿到有限候选。候选过滤、冷却判断和已发布状态应由索引支持，复杂排序可以在应用层完成。不能为每次抽卡重新扫描用户全部行为。

## 11. 权限、隐私和内容安全

角色建议分为：

- 内容编辑：创建和修改草稿，提交审核。
- 审核人员：审核 Agent 提案、批准试玩和发布。
- 数据人员：查看聚合指标和实验结果，不能修改内容。
- 分发管理员：调整复用策略和探索比例，所有调整留痕。
- 系统管理员：维护标签、状态和权限。

用户行为用于推荐时，默认使用内部用户 ID，不保存不必要的聊天原文。原始玩法需要保留来源和证据级别。Agent 从外部采矿时记录 URL、来源类型、是否需要重新表达和版权风险。

审核必须关注身体接触、羞辱、隐私暴露、危险行为、未成年人适用性和外部 AI 误导。安全风险高的卡即使数据表现好，也不能自动提升分发。

## 12. 分阶段开发计划

### Phase 1：数据和状态基础

- 建立内容实体、版本、来源和 L1/L2 关系。
- 建立游戏卡实例和游戏局状态。
- 区分匿名 Card Delivery 与需要持久化的 Game Card Instance，不为普通轻玩创建数据库游戏局。
- 建立 L2 复用策略和用户暴露状态。
- 建立 L1/L2 暴露聚合、匿名 actor 幂等和登录续接。
- 建立版本审核状态、发布版本锁定和卡片实例快照。
- 建立统一事件字典和幂等写入。

### Phase 2：管理端最小闭环

- 原始样本库。
- L1 工作台。
- L2 内容池。
- 游戏卡实验室。
- 审核队列。
- 分发策略页面。

### Phase 3：规则推荐和数据分析

- 候选过滤。
- L1/L2 冷却。
- 用户收藏和偏好。
- 基础排序。
- L1/L2 分层指标。
- 管理端数据总览。

### Phase 4：Agent 协作和智能推荐

- Agent 任务与提案。
- 版本差异和审核流。
- 小流量探索。
- 上下文推荐。
- Bandit 或其他模型实验。
- 推荐原因和模型效果复盘。

## 13. 开发验收标准

第一版完成后，必须能够：

1. 创建一个 L1，并发布至少一个版本。
2. 为一个 L1 创建结构化 L2 内容包。
3. 组合成用户真实可玩的游戏卡。
4. 抽卡时排除当前用户已冻结或已消耗的内容。
5. 完成后正确记录展示、开始、完成、跳过和重抽事件。
6. 收藏 L1 后提高该类玩法的推荐倾向。
7. 同一 L1 再玩时更换 L2，并保持 L1 统计独立。
8. 管理员修改冻结策略后能追踪和回滚。
9. Agent 提案不能绕过审核直接发布。
10. 历史游戏局不受后来内容编辑影响。
11. 行为数据增长时，卡片读取不依赖扫描事件明细。
12. 事件重复提交不会重复增加展示或完成次数。

## 14. 当前设计中的明确取舍

- “极致好玩”由内容审核和真人试玩保证，推荐系统只负责更好地匹配和学习。
- 用户收藏 L1，具体 L2 按内容策略消耗和冷却。
- L0 保留在研发和分析侧，不进入用户抽卡。
- 推荐先用规则和统计，数据量足够后再引入模型。
- 管理员可以调节复用策略，但必须有范围、日志和回滚。
- Agent 负责扩大探索和降低编辑成本，人工保留最终发布权。
- 内容版本、运行实例和行为事件分开，保证历史可还原和线上性能稳定。
