# React 用户端第一阶段

## 目标与边界

在 `apps/player` 建立独立 React + TypeScript + Vite 用户端，先复刻 Playbit-design 的视觉和交互，再按页面接入已有后端。视觉基线为设计仓库提交 `49c8f21`。现有 `apps/web`、`apps/api`、数据库和根 Vercel 配置保持原有运行方式。

新的用户流程优先于旧文档中已经过时的页面组织：默认打开游戏卡；顶部切换玩/约；底部为权益、Playbit、我的。玩与约不强制互跳，结果进入权益体系。L0/L1/L2 仍是研发语言。

当前只读本地样本，不登录、不调用生产 API、不生成真实合同或卡券。演示数据仅属于新用户端独立的本地命名空间。阶段二接 API 时替换 repository 和页面数据适配，不把展示模型等同于数据库实体。

## 工程约定

- React 19、Vite 7 延续仓库工具链；使用 React Router 处理直接访问、刷新和返回，Radix Dialog 处理焦点、Escape 和遮罩，lucide-react 延续图标库。
- `app` 只编排，`pages` 组织页面，`features` 管理交互，`data` 存样本，`services` 隔离本地存储和分享，公共文案进入 `packages/content/src/player.ts`。
- 保留基础 token、产品 token、公共控件与局部布局分层的范式；新旧前端视觉变量不强制同值，避免旧视觉反向覆盖 Figma 设计。
- CSS 整理成最终规则，不继承原型多轮追加覆盖；资源不引入第三方热链、base64 装饰图片或远程字体依赖。签名字迹是运行时矢量笔画数据。
- 页面就绪后即对照旧实现，确定项直接补充；争议项记入下表，不阻断开发。每个阶段用截图与主流程验证。

## 第二轮业务对照审查

本节按旧 Vue 用户端的实际代码能力，对照新 React 用户端当前的页面和状态。这里的“保留”指保留业务能力，不代表保留旧页面的布局；“舍弃”指不迁移旧入口或旧机制；“讨论”指在接入后端、确定数据模型前必须做产品判断。

### 先给结论

新端的业务主入口已经确定：打开即进入游戏内容，`约模式` 是同等重要但独立的低频仪式流程，权益是两者可以共同进入的结果资产。旧端不能整体搬迁，因为旧端首页把游戏、合同、账户、历史和权益当成服务入口，新端要把游戏卡作为内容消费入口。

但新端目前仍有四个不能用“视觉复刻”掩盖的业务缺口：

1. 新端只有卡片展示和本地切换，还没有旧端已经验证过的独立游戏运行闭环：工具、跨卡计分、结果记录、证书和行为事件。
2. 新端把约模式结算直接写成本地 `Coupon`，没有区分正式 Agreement、游戏结果证书和独立结算权益，后续接 API 时会造成状态模型重构。
3. 新端权益页只有“赢得 / 输掉”两个视图，旧端的“已发出 / 待领取 / 可履约 / 已履约”等状态被压扁，无法支撑独立发券和领取。
4. 新端个人页仍有通知、账户、安全等点击后只弹提示的入口。这些不是暂存能力，而是会让用户误以为产品已有对应服务，应在本阶段删掉或改成明确不可用的设置入口；当前产品方向更适合删掉。

因此，下一轮开发优先级不是继续补旧页面，而是先补齐游戏结果和权益边界，再接入推荐与正式身份能力。

### 1. 游戏首页与卡片消费

| 业务点 | 旧 Vue 实际能力 | 新 React 当前实现 | 建议结论 |
| --- | --- | --- | --- |
| 默认入口 | 旧首页同时承载立合约、抽卡、历史、账户和权益快捷入口；抽卡后进入独立游戏页 | `/` 直接显示卡背/卡面、场景、换卡、喜欢和添彩头 | **保留新入口**。打开即玩是产品最锋利的定位，旧首页多入口结构舍弃 |
| 场景筛选 | 旧端主要通过推荐卡和卡片属性进入游戏 | 新端支持场景、用户卡组和最多三组展示 | **保留**。场景是分发入口，不应退化成静态标签；后端需记录选择、跳过和进入结果 |
| 卡片推荐 | 旧端支持远端推荐、`previousIds`、偏好 L1、抽卡事件 | 新端目前从本地 demo 池选择卡片 | **保留旧能力，替换实现**。推荐请求只返回一张已冻结卡片快照，不把本地 demo 选择逻辑作为生产契约 |
| 换一张 | 旧端是 reroll，有 `rerolled` 事件和最近卡片排除 | 新端通过本地卡池上下翻页 | **保留**。需要明确“换一张”是切换 L1，不能误记为完成；后端记录曝光、跳过和换卡原因 |
| 再玩一局 | 旧端可以偏好同一 L1，换一条 L2 内容 | 新端当前是本地卡池内切换，尚未表达同 L1 新内容语义 | **需要讨论后定为推荐契约**。产品文案应是“同一种玩法再来一张”，而不是重复展示同一内容 |
| 喜欢 | 旧端按 L1 同步喜欢状态，并用于推荐 | 新端喜欢状态目前属于本地卡组/卡片展示状态 | **保留 L1 喜欢**。喜欢的是玩法，不是某一次卡片实例；卡片收藏和用户自建卡组要分开 |
| 彩头 | 旧端已有从游戏结果进入结算/协议的历史路径；新边界已改为线下约定、平台只记录结果和发券 | 新端在卡面上保存一段 stake 文本，并直接影响本地权益演示 | **需要讨论语义**。卡面可以保留“彩头预告/本局备注”，但不能暗示已经锁定权益或自动生成券；实际权益必须从结果页或独立发券入口产生 |
| L0/L1/L2 | 旧端展示模型没有把研发分层暴露给用户 | 新端卡面也未暴露分层 | **保留为后台/推荐语言**。用户端只显示可理解的玩法和内容，不把 L0/L1/L2 变成筛选项或卡片字段 |

### 2. 独立游戏运行页、工具与结果

这是旧端最值得迁移的部分。旧端 `useStandaloneGameFlow` 已经把临时局、工具和结果拆开，当前新端还没有对应 React 运行状态。

| 业务点 | 旧 Vue 实际能力 | 新 React 当前状态 | 建议结论 |
| --- | --- | --- | --- |
| 开局与临时局 | 创建 session，记录开始、暴露、离开、完成；支持匿名运行 | 只有卡片翻面和本地页面状态 | **P0 保留**。先把匿名临时局和完成幂等契约接入，不能以页面停留推断完成 |
| 工具声明 | 卡片声明 `timer/counter/scoreboard`，没有声明时按卡片属性推断 | 新端暂无实际工具运行区 | **P0 保留**。工具是卡片可选辅助能力，按卡片动态展示，不做所有卡片固定显示 |
| 计时器 | 暂停、继续、清零，显示毫秒 | 新端暂无 | **P0 保留**。计时基于真实时间戳，不用渲染次数计时 |
| 计数器 | 当前局内加减，离开局后可重置 | 新端暂无 | **P0 保留**。属于卡片工具状态，不进入推荐用户画像 |
| 记分牌 | 最多 8 人、改名、加减分、跨卡持久化、手动清空 | 新端暂无 | **P0 保留**。它跟随整个游戏，不跟随单张卡；清空必须二次确认，数据默认保存在浏览器直到用户手动清空或浏览器清理 |
| 结果模型 | 双人 winner、多人 ranking、无胜负 completed；结果由主持人登记 | 新端约模式只有甲乙 winner | **P0 保留轻量游戏结果**。结果记录与正式 Agreement 分开；多人只做主持人登记的排名，不做房间和在线裁判 |
| 证书 | 旧端支持游戏结果、正式协议、履约、翻盘、豁免等多种证书 | 新端协议页只有本地文档视觉；游戏证书尚未接入 | **P1 保留游戏结果证书**。证书是主持人分享的结果快照，不证明权益已发放；其他玩家不必回到游戏页确认 |
| 行为采集 | 暴露、开始、工具打开、换卡、完成、离开、喜欢等事件 | 新端本地没有可上报事件 | **P0/P1 保留**。推荐读取聚合，不在请求时扫描事件明细；先建立事件名和幂等键，再接模型 |
| `play again` | 结果后再开一局，并记录新 session | 新端主要是卡面切换 | **保留并拆清**。它是新局，不是修改旧结果，也不是重新结算 |
| 工具分析 | 旧端工具是用户辅助，不是成熟的运营分析模块 | 新端没有 | **舍弃后台工具分析**。只采集必要使用事件，除非未来证据证明工具影响留存或完成率 |

### 3. 约模式、协议与正式签约

| 业务点 | 旧 Vue 实际能力 | 新 React 当前实现 | 建议结论 |
| --- | --- | --- | --- |
| 入口 | 旧首页与游戏入口混在一起 | 顶部切换到 `/promise`，游戏和约模式职责分开 | **保留新结构**。游戏不强制签约，签约也不自动进入游戏 |
| 创建约定 | 标题/挑战、权益选择、创建草稿、登录校验 | 本地填写文本和权益，进入本地签名步骤 | **保留能力，改造域边界**。权益仍用已有权益选择组件，不重复设计权益名称和履约说明字段 |
| 签字 | 旧端发起人签署，分享给对方异步签署，保存 revision 并校验变更 | 新端同设备甲乙双方签名，本地保存 | **原型保留；正式形态需讨论**。同机双签可以用于验证仪式感，但不能直接当成线上正式签约模型 |
| 协议变更 | 旧端有 revision、事件同步、签署状态冲突处理 | 新端没有远端同步 | **保留在正式协议域**。不进入轻量游戏结果，也不在本地 demo 阶段伪造同步成功 |
| 彩头追加 | 旧端 active 协议支持 boost，双方确认或撤回，最多三次 | 新端没有 | **建议舍弃轻量游戏路径；正式协议保留待讨论**。加注是正式协议的修订能力，和游戏卡彩头不是同一流程 |
| 结算 | 旧端 Session 记录协议结果，Settlement 展示证书并关联权益 | 新端约模式选赢家后直接生成本地 Coupon | **需要重构**。协议结算、游戏结果记录、独立权益发放必须是三个可独立完成的动作 |
| 协议详情 | 旧端正式协议有参与者、状态、revision、历史；新端本地文档有签名、日期、印章和分享 | **保留新端表达，补后端真相**。详情页可以继续是仪式化文档，但状态必须来自 Agreement，而不是通过本地 coupon 推断 |
| 游戏反向签约 | 旧端曾存在 card source agreement 路径 | 新产品已确定游戏不进入约模式 | **建议舍弃**。游戏结果可生成证书或独立结算，不为“想加彩头”的用户强制创建正式协议 |

### 4. 权益中心、独立发券与领取

| 业务点 | 旧 Vue 实际能力 | 新 React 当前实现 | 建议结论 |
| --- | --- | --- | --- |
| 权益入口 | 旧端有独立权益中心和详情 | 新端有 `/benefits` 底部导航 | **保留**。权益不是约模式的附属页，而是游戏和签约共同进入的结果中心 |
| 状态分类 | `all / issued / pending / available / used`，并按发行人/持有人展示 | 仅 `won / lost` 两个 tab，状态仅 `available / redeemed` | **P0 需要讨论并重构**。用户端可以采用更易懂的“我获得的 / 我发出的”，但底层必须保留 `issued → claimed → active → fulfilled / revoked / expired` |
| 我的签发 | 旧端有 IssueVoucher，发券后分享链接，未领取前可删除 | 新端无独立发券流程 | **P0 保留**。可从权益中心固定入口进入；创建时不要求填领取人，使用领取次数和分享码 |
| 领取 | 旧端公开 claim 页面，领取时再绑定账号，重复扫码返回同券 | 新端无领取入口 | **P0 保留**。未登录可以查看公开券，只有领取/创建/履约等操作再引导登录；不能把登录放在展示入口前 |
| 领取次数 | 旧端支持默认一次、可调上限 | 新端无 | **P0 保留**。次数是券发行属性，不是共享券；每次领取要有唯一性与并发校验 |
| 删除未领取券 | 旧端支持发行人删除未领取券 | 新端无 | **P0 保留**。只有 `ISSUED` 且没有领取记录时允许撤回/删除 |
| 核销/履约 | 旧端持有人核销，有状态和冲突处理 | 新端只有本地 redeem | **P1 保留**。先明确“领取并同意”和“实际履约/核销”是两个动作，不要用一个按钮完成两种语义 |
| 翻盘 | 旧端有 Flip：履约方发起、对方接受/拒绝、输赢影响原券和新券 | 新端有简单 replay 入口但没有真实状态 | **P2 讨论**。它是权益域长尾，不阻塞首版游戏和独立结算；若保留必须沿用独立券身份，不能复制成第二套 coupon |
| 赖皮券 / grace | 旧端有 10 次履约里程碑、申请豁免、双方确认 | 新端没有 | **建议暂时舍弃用户入口，保留数据扩展位**。它不是当前 Playbit 最锋利的首要循环，后续用真实履约数据验证是否值得恢复 |
| 权益与来源 | 旧端部分 coupon 要求 `agreement_id`，但产品边界已允许游戏结果、独立备注或无来源 | 新端 Coupon 只支持可选 `agreementId`，没有 provider/holder/claim 状态 | **P0 必须先定模型**。不把独立发券塞进 Agreement；来源可为空，备注可为空，券仍要有发行人、领取人/待领取状态和权益条款 |

### 5. 我的、记录、历史与账户

| 业务点 | 旧 Vue 实际能力 | 新 React 当前实现 | 建议结论 |
| --- | --- | --- | --- |
| 我的场景卡组 | 旧端没有成熟的新卡组消费入口 | 新端有自建卡组、喜欢卡片和最多展示三组 | **保留并继续打磨**。它是推荐反馈和用户内容组织，不应与后台 L1/L2 概念混同 |
| 卡组详情 | 新端点击个人卡组目前主要是提示，不真正打开卡组 | 只有 `notify` 反馈 | **P0/P1 需要补**。如果入口保留，就必须能回到首页并以该卡组作为池；否则先删掉“可点击”的假入口 |
| 协议记录 | 旧端有 History，按状态筛选、月份分组、删除草稿/未完成协议 | 新端个人页只显示第一条协议详情入口 | **P1 保留简化历史**。至少要有协议列表、状态、时间和详情；不要把所有游戏结果混入正式协议列表 |
| 游戏记录 | 旧端主要由协议/游戏结果流程承载 | 新端尚未有记录列表 | **需要讨论**。推荐先做“本机最近结果/证书”而非把它和合同记录混成一个列表；历史是否云端保存取决于登录和证书分享需求 |
| 账户资料 | 旧端昵称、头像、签名、登录/退出和远端保存 | 新端只有本地昵称编辑 | **保留账户基础能力，延后正式登录**。不要在游客开始游戏时强制登录；创建发券、领取、签约正式提交时再引导 |
| 通知 | 旧端有账户/通知入口，但当前新端点击只显示提示 | 新端有通知按钮但无通知系统 | **建议舍弃当前假入口**。真正需要时再以登录后的待签署、待领取、待履约事件为依据重新设计 |
| 账户与安全 | 旧端有入口；新端按钮没有实际页面 | 新端只 toast | **建议舍弃当前假入口**。在没有身份、设备管理和安全策略前不展示 |
| 退出 | 旧端有明确登出 | 新端没有真正账户会话 | **延后**。本地原型不伪造登录态；接入身份后再实现 |

### 6. 分享、深链接与未登录边界

旧端已经验证了三种公开入口：待签协议分享、独立权益领取、证书/结果分享。新端当前只有本地协议分享文案，不能直接把它当成线上分享完成。

建议统一以下边界：

- 展示和查询类页面可匿名打开：游戏首页、卡片、公开证书、权益券预览、合约/权益公开详情。
- 需要产生归属或状态变化的动作才判断登录：正式创建协议、签署、创建权益券、领取权益、履约/核销、保存需要跨设备的结果。
- 分享必须区分“复制了链接/唤起系统分享”和“服务端已经生成可访问的公开记录”；前端不能在本地 demo 中显示真实送达或真实入账。
- 游戏结果的参与者可以只有昵称快照，未登录不强行创建账号；证书明确“由主持人登记”。

## 跨页面能力分类

### 建议保留并优先迁移

1. 打开即玩、匿名游戏、场景选择、卡片翻面、换卡、喜欢 L1、同玩法再来一张。
2. 卡片声明工具：计时器、计数器和跨卡记分牌；工具状态和游戏结果状态分离。
3. 临时局、曝光/开始/完成/离开/换卡/喜欢等行为事件，以及匿名幂等和完成校验。
4. 双人胜负、多人排名、无胜负完成三种结果模型；主持人登记，不做房间。
5. 游戏结果证书和正式协议证书分开，证书分享不等于权益发放。
6. 独立权益中心、独立发券、分享领取、领取次数、未领取撤回、持有人履约。
7. 约模式的签字、盖章、协议详情和正式记录；它作为独立入口，不成为游戏必经步骤。
8. 喜欢、换卡、完成、证书打开等可用于推荐和内容研发的行为数据。

### 需要产品讨论后再固化

1. 卡片上的“添个彩头”到底是本局备注、预设权益，还是直接进入独立发券；当前建议保留入口，但明确“不自动锁定、不自动发券”。
2. “再玩一局”是否严格按同一 L1 返回新的 L2 内容，以及在内容不足时的回退策略。
3. 游戏结果是否长期进入个人历史；建议先保存主持人可分享的结果快照，登录后再提供跨设备历史。
4. 正式签约是否继续支持异步邀请、revision、实时同步；原型同机双签不能直接替代正式协议。
5. Agreement 的 `boost` 是否只保留在正式约模式；当前不建议进入普通游戏卡。
6. 权益中心的用户视图采用“我获得的 / 我发出的”，还是保留更细的“待领取 / 可履约 / 已履约”；底层状态不能删减。
7. 翻盘和赖皮券是否属于首发核心循环；目前建议延后，用履约数据验证。
8. 用户自建卡组是否允许公开分享、二创和进入推荐池；当前只保留私有卡组和喜欢反馈。

### 建议舍弃或删除假入口

1. 旧首页的多入口服务总览作为默认首页。
2. 游戏必须先创建协议、签字或登录才能开始。
3. 游戏卡与正式 Agreement 强行一一绑定。
4. 把多人游戏做成在线房间、加入房间、平台判定和权益自动分配。
5. 把工具使用做成独立后台分析板块。
6. 新端个人页中没有实际页面和数据支持的通知、账户、安全按钮。
7. 只弹 toast 的“卡组详情”“设置”“历史”等假交互。
8. grace waiver、flip 等长尾机制在首版迁移中阻塞主流程。

## 接后端前的模型提醒

当前 React 的 `PlayerState` 适合视觉和交互验证，不适合作为生产领域模型。尤其不能继续沿用以下等价关系：

```text
约模式 winner -> 本地 Coupon
游戏卡 stake -> 已经存在的权益
权益 won/lost -> 券的发行/领取状态
协议详情 -> 当前本地草稿
```

接入后端时至少保持以下对象边界：

```text
ContentCard / L1 / L2 / Tool
  -> PlaySession -> GameResultRecord -> Certificate

Agreement -> Signature / AgreementResult -> AgreementCertificate

Settlement / Coupon -> Claim -> Fulfillment
```

游戏结果可以可选引用卡片、协议或结算，但不复制协议和券的状态。独立结算的来源可以是游戏结果、正式协议或一条可空的转让备注；`agreement_id`、结果引用和备注都可以为空，但券本身不能缺少发行方、权益条款和领取/履约状态。
